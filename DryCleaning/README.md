## Состав решения

```text
DryCleaning/
├── DryCleaning.slnx
├── src/
│   ├── DryCleaning.Domain/
│   │   ├── Client.cs, Item.cs, ItemCategory.cs, Order.cs
│   │   ├── Enum/                 # статусы заказов и виды обработки
│   │   ├── Interfaces/           # интерфейсы репозиториев
│   │   └── Seeds/TestData.cs      # исходные данные
│   ├── DryCleaning.Contracts/
│   │   ├── Dto/                  # данные запросов и ответов, атрибуты валидации
│   │   ├── Interfaces/           # интерфейсы сервисов
│   │   └── Exceptions/           # исключения для запретов удаления
│   ├── DryCleaning.Application/
│   │   └── Services/             # бизнес-правила, преобразование в DTO и аналитика
│   ├── DryCleaning.Infrastructure.InMemory/
│   │   └── Repositories/         # работа с коллекциями в памяти
│   └── DryCleaning.Api/
│       ├── Controllers/          # HTTP-маршруты и обработка ошибок
│       ├── Properties/launchSettings.json
│       ├── Program.cs            # регистрация зависимостей и настройка API
│       └── DryCleaning.Api.http   # примеры запросов
└── tests/
    └── DryCleaning.Tests/         # пять тестов аналитических LINQ-запросов
```

Контроллеры получают интерфейсы сервисов через конструктор и работают с DTO. Сервисы проверяют данные, выполняют бизнес-правила и аналитические запросы, обращаются к репозиториям и преобразуют доменные объекты в DTO. Репозитории читают и изменяют коллекции `TestData`.

Интерфейсы репозиториев находятся в Domain, а их реализации — в Infrastructure.InMemory. Интерфейсы сервисов находятся в Contracts, реализации — в Application. Все операции сервисов и репозиториев возвращают `Task`. В `Program.cs` зарегистрированы все четыре сервиса и четыре репозитория.

При запуске `TestData` создаёт 10 клиентов, 10 категорий, 20 изделий и 20 заказов. API использует один экземпляр этих данных. Созданные и изменённые записи не сохраняются на диск и возвращаются к исходному состоянию после перезапуска приложения.

## DTO и проверки данных

| Сущность | Ответ API | Создание | Изменение |
|---|---|---|---|
| Клиент | `ClientDto` | `ClientEditDto` | `ClientEditDto` |
| Категория | `ItemCategoryDto` | `ItemCategoryEditDto` | `ItemCategoryEditDto` |
| Изделие | `ItemDto` | `ItemEditDto` | `ItemEditDto` |
| Заказ | `OrderDto` | `OrderCreateDto` | `OrderEditDto` |

DTO заказа содержит `ClientDto` и `ItemDto`, а DTO изделия — `ItemCategoryDto`. Доменные сущности из API не возвращаются.

Входные DTO используют атрибуты валидации. Имя клиента ограничено 100 символами, телефон — 20 символами и проверяется атрибутом `[Phone]`. Название категории ограничено 50 символами, цена должна быть больше нуля и не превышать 10 000 000. Название и материал изделия ограничены 100 символами. Идентификаторы связанных записей и плановый срок обработки должны быть положительными, виды обработки и статусы — допустимыми значениями enum.

Существование связанных записей, запреты удаления и соответствие даты завершения статусу заказа проверяются в сервисах. Ошибки выполнения операций записываются через `ILogger`; при неожиданной ошибке контроллер возвращает `500` без внутренних деталей исключения.

## REST API

Для каждой сущности доступны `GET` списка, `GET` по ID, `POST`, `PUT` по ID и `DELETE` по ID.

| Сущность | Список и создание | Получение, изменение и удаление по ID |
|---|---|---|
| Клиенты | `/api/clients` | `/api/clients/{id}` |
| Категории | `/api/categories` | `/api/categories/{id}` |
| Изделия | `/api/items` | `/api/items/{id}` |
| Заказы | `/api/orders` | `/api/orders/{id}` |

Заказы ссылаются на существующих клиентов и изделия, а изделия — на существующие категории. Нельзя удалить клиента или изделие с заказами либо категорию с изделиями: сервер возвращает `409 Conflict`. Для некорректных данных используется `400 Bad Request`, для отсутствующей записи — `404 Not Found`. Успешное создание возвращает `201 Created`, а изменение и удаление — `204 No Content`.

Новый заказ получает статус `Accepted` и время приёма в UTC. При изменении заказа дата завершения обязательна для статусов `Completed` и `Issued`, а для остальных статусов должна быть пустой. Передаваемая дата завершения должна содержать `Z` или смещение часового пояса и не может быть раньше даты приёма.

Для получения связанных записей доступны:

- `GET /api/clients/{clientId}/orders` — заказы клиента;
- `GET /api/categories/{categoryId}/items` — изделия категории.

Если клиент или категория существуют, но связанных записей нет, возвращается `200 OK` с пустым массивом. Если клиент или категория не найдены — `404 Not Found`.

## Аналитические запросы

| Маршрут | Результат на исходных данных |
|---|---|
| `GET /api/orders/in-progress` | Заказы в обработке, отсортированные по дате приёма: ID 1, 12, 9 |
| `GET /api/clients/top?start=2025-09-15&end=2026-09-15` | Пять клиентов по числу принятых изделий: ID 1, 2, 3, 4, 5; количества 4, 4, 3, 2, 1 |
| `GET /api/clients/top-spender` | Клиент 2, сумма выданных заказов 6700 |
| `GET /api/clients/longest-processing` | Клиенты 1 и 4, максимальная длительность 19 дней |
| `GET /api/categories/popularity?end=2026-03-01` | Наиболее популярные категории: ID 8, 3, 6, 4, 1; наименее популярные: ID 2, 9, 3, 6, 4 |

В запросах за период начальная дата включается, конечная — нет. Для рейтинга клиентов параметры `start` и `end` обязательны; отсутствие любого из них возвращает `400 Bad Request`. Отменённые заказы не участвуют в рейтингах клиентов и категорий. Категории без заказов участвуют в рейтинге наименее популярных. Расходы клиента считаются по текущей цене категории изделия.

## Запуск и проверка

Требуется .NET SDK 10. Из папки `DryCleaning` запустить API:

```powershell
dotnet run --project .\src\DryCleaning.Api\DryCleaning.Api.csproj --launch-profile https
```

Профиль `https` запускает сервер на `https://localhost:3622` и `http://localhost:3621`. В Visual Studio можно открыть [DryCleaning.slnx](DryCleaning.slnx), выбрать `DryCleaning.Api` запускаемым проектом и профиль `https`. В режиме Development Swagger UI доступен по адресу `https://localhost:3622/swagger`, а описание OpenAPI — по адресу `https://localhost:3622/openapi/v1.json`.

Для ручной проверки открыть [DryCleaning.Api.http](src/DryCleaning.Api/DryCleaning.Api.http). Там собраны успешные запросы и примеры ошибок. Запросы на создание и последующее изменение записей рассчитаны на исходные данные, поэтому их удобнее выполнять по порядку после запуска приложения.

Для запуска пяти тестов xUnit v3 из той же папки:

```powershell
dotnet test .\DryCleaning.slnx
```

Тесты проверяют аналитические LINQ-запросы из первой лабораторной работы на фиксированном наборе данных. Они не отправляют HTTP-запросы к API.
