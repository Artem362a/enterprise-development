## Реализация

Модель описывает клиентов химчистки, принятые изделия, их категории и заказы. Данные хранятся в коллекциях в памяти. Пять запросов из задания реализованы с помощью LINQ и проверяются тестами xUnit v3.

| Тип | Назначение |
|---|---|
| `Client` | Клиент: идентификатор, ФИО и телефон |
| `Item` | Изделие: идентификатор, название, материал и категория |
| `ItemCategory` | Категория: идентификатор, название, рекомендуемый способ обработки и цена |
| `Order` | Заказ: идентификатор, клиент, изделие, статус, дата приёма, срок в днях и фактическая дата завершения |
| `OrderStatus` | Статусы: принят, в обработке, обработан, выдан, отменён |
| `CleaningType` | Способы обработки: химчистка, аквачистка, обработка паром, ручная стирка и глажение |

Один заказ относится к одному изделию. Заказы ссылаются на существующих клиентов и изделия, а изделия — на категории из справочника. Обязательные свойства помечены `required`; дата завершения заказа допускает `null`. Публичные типы и их члены снабжены XML-комментариями на английском языке.

## Тестовые данные

[TestData](DryCleaning.Domain/TestData.cs) создаёт фиксированный набор вымышленных данных:

| Коллекция | Количество |
|---|---|
| Клиенты | 10 |
| Категории изделий | 10 |
| Изделия | 20 |
| Заказы | 20 |

В наборе есть повторные обращения клиентов, разные статусы заказов, заказы внутри и за пределами выбранных периодов, а также клиент без заказов. Заказы 2, 3 и 14 обрабатывались по 19 дней: два из них относятся к одному клиенту. Это позволяет проверить равную максимальную длительность у нескольких клиентов и отсутствие повторов в результате.

Тестовые классы получают данные через `IClassFixture<TestData>`. xUnit создаёт отдельный экземпляр `TestData` для каждого тестового класса и использует его во всех тестах этого класса. Тесты только читают общие данные.

## Аналитические тесты

В решении пять методов `[Fact]`, по одному на каждый пункт задания. Внутри каждого теста сначала задаются входные и ожидаемые значения, затем выполняется LINQ-запрос, после чего результат проверяется через `Assert` — схема Arrange → Act → Assert.

| Запрос | Что проверяется | Ожидаемый результат |
|---|---|---|
| Заказы в обработке | Состав заказов и сортировка по дате приёма | ID: 1, 12, 9 |
| Топ-5 клиентов по числу изделий за период | Клиенты, порядок и количество принятых изделий | ID: 1, 2, 3, 4, 5; количества: 4, 4, 3, 2, 1 |
| Клиенты с самой долгой обработкой | Максимальная длительность, отсутствие повторов и сортировка по ФИО | Клиенты 1 и 4; 19 дней |
| Топ-5 наиболее и наименее популярных категорий за год | Обе пятёрки, их порядок и число заказов, включая нулевые значения | Наиболее: ID 8, 3, 6, 4, 1, количества 2, 1, 1, 1, 1; наименее: ID 2, 9, 3, 6, 4, количества 0, 0, 1, 1, 1 |
| Клиент с наибольшими расходами | Клиент и общая стоимость выданных заказов | Клиент 2; 6700 рублей |

Для топа клиентов выбран период **с 15.09.2025 по 15.09.2026**, для популярности категорий — **с 01.03.2025 по 01.03.2026**. Начало включается, конец не включается. Остальные запросы используют всю историю заказов.

В тестах рейтинга клиентов и максимальной длительности заказы перечисляются в обратном порядке. Ожидаемые результаты заданы явно, поэтому проверки не зависят от исходного порядка коллекции. Отдельных тестов пустых выборок нет.

## Принятые правила

- Один заказ считается одним приёмом изделия.
- В рейтингах клиентов и категорий отменённые заказы исключаются. Остальные учитываются по дате приёма.
- «Последний год» означает 12 месяцев перед заданной датой. Начало вычисляется через `AddYears(-1)`; текущее системное время не используется.
- Фактическая длительность обработки равна `CompletedDate - AcceptDate`. Учитываются заказы со статусами `Completed` и `Issued` и заполненной датой завершения. `ProcessingDays` хранит обещанный срок.
- При равной максимальной длительности возвращаются все соответствующие клиенты, каждый один раз.
- В наименее популярные категории входят категории без заказов за выбранный год. Две пятёрки могут пересекаться при равных количествах.
- При равенстве количества или суммы результат упорядочивается по имени клиента или названию категории, затем по ID. Для строк используется `StringComparer.Ordinal`, для заказов с одинаковой датой — сортировка по ID.
- Выданный заказ (`Issued`) считается оплаченным. Расходы рассчитываются по `Item.Category.Price`; тарифы в рамках лабораторной считаются неизменными. При изменяемых тарифах понадобится хранить цену на момент заказа.
- Цены и рекомендуемые способы обработки в датасиде условные.

## Требования к среде

- .NET SDK 10.0.
- Visual Studio Community 2026 с поддержкой .NET, если используется IDE.
- Доступ к NuGet при первом восстановлении зависимостей.

## Запуск в Visual Studio

1. Открыть [DryCleaning.slnx](DryCleaning.slnx).
2. Сохранить файлы и собрать решение.
3. Открыть **Тест → Обозреватель тестов**.
4. Запустить все тесты проекта `DryCleaning.Tests`.

Ожидаемый результат: **5 успешно пройденных тестов**.

## Запуск из терминала

Из корневой папки репозитория `enterprise-development`:

```sh
dotnet test DryCleaning/DryCleaning.slnx --configuration Release
```

Команда восстанавливает зависимости, собирает решение и запускает тесты. При успешном выполнении она завершается с кодом `0` и сообщает о пяти пройденных тестах.

## GitHub Actions

Workflow [Lab 1 tests](../.github/workflows/lab1-tests.yml) запускается при отправке коммитов (`push`) и открытии или обновлении pull request.

На Ubuntu выполняются получение кода, установка .NET SDK 10.0 и команда `dotnet test` в конфигурации `Release`, которая восстанавливает зависимости, собирает решение и запускает тесты.

Результат проверки доступен во вкладке **Actions → Lab 1 tests** и в разделе **Checks** соответствующего PR. Запуск на GitHub происходит после отправки изменений в репозиторий.
